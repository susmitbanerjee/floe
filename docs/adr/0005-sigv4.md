# 0005. SigV4 signing for Glue and S3 Tables

- Status: Accepted
- Date: 2026-11-19

The prompt names this ADR 0002; ADRs 0002 to 0004 already exist, so it is 0005.

## Context

AWS Glue's Iceberg REST endpoint (`https://glue.<region>.amazonaws.com/iceberg`) and S3 Tables
authenticate every request with AWS Signature Version 4. Iceblink needs one concrete signer, with
credentials from the standard AWS chain, attached to the pinned iceberg-catalog-rest 0.11
client. Findings on 2026-11-19:

- **apache/iceberg-rust#2311** ("feat(rest): Add support for AWS SigV4 signing") was **closed
  unmerged** on 2026-08-27 by the stale bot, after going unreviewed. It was never released.
  Its thread recorded what Glue needs: a real `x-amz-content-sha256` body hash (Glue refuses
  `UNSIGNED-PAYLOAD`), and application headers kept out of the signature. Issue #1236 ("REST
  catalog: support AWS sigV4") is still open.
- **0.11 has a released signing hook.** `AuthManager`/`AuthSession::authenticate(&mut
  HttpRequest)` exposes the method, the full URL, mutable headers, and the body bytes. Its docs
  say this is for signers. iceberg adds content-type, user-agent and x-client-version *after*
  `authenticate`, so they stay unsigned.
- **iceberg 0.11 joins names into paths raw**, without percent-encoding. A `%`, `/`, `?` or `#`
  in a namespace or table name corrupts the URL, signed or not.
- **aws-config 1.13.3's default chain doesn't cache.** SDK clients cache in an `IdentityCache`,
  which needs SDK runtime components to use from outside.
- **aws-config's default HTTPS client is rustls on aws-lc**, a C build with an
  OpenSSL-licensed component.

## Options

- **A. Implement the released hook.** It exists in 0.11.
- **B. Sign inside Iceblink's own `reqwest::Client`** or middleware. reqwest 0.12 has no middleware,
  and the hook makes this unnecessary.
- **C. A `[patch.crates-io]` git pin carrying #2311.** It was never merged, and it isn't needed.

## Decision

**Option A.** `iceblink-catalog::sigv4::AwsSigV4Signer` implements `AuthManager`/`AuthSession`,
signing with the `aws-sigv4` crate:

- **What's signed:** the method, the full URL, `host`, `x-amz-date`, `x-amz-content-sha256`
  (SHA-256 of the actual body) and, for temporary credentials, `x-amz-security-token`. Nothing
  else.
- **Path encoding:** the canonical path is percent-encoded twice, as SigV4 requires for every
  service but S3 (aws-sigv4's default).
- **Credentials:** aws-config's default chain (environment, profile, SSO, web identity,
  container and instance roles), with an optional profile from `[catalog.sigv4] profile`.
- **Credential cache (deviation, maintainer's choice):** the prompt said not to add a cache, but
  the provider doesn't cache. The signer keeps the last credentials and refreshes them through
  the provider when they expire within 5 minutes, one refresh at a time. Without it, every
  catalog request could hit STS, SSO or instance metadata.
- **Name encoding (maintainer's choice):** Iceblink percent-encodes each namespace and table name
  before iceberg builds the path. Only `A-Z a-z 0-9 - _ . ~` stay unencoded. It puts the real
  name back on the loaded table. This fixes odd names for every catalog, not only signed ones.
- **TLS:** aws-config is built without default features. Iceblink passes an
  aws-smithy-http-client on rustls with ring, so aws-lc isn't in the build. `credentials-process`
  is off as well.
- **Errors:** `connect` resolves credentials once, so a missing AWS identity fails at startup with
  a hint (AWS_PROFILE, `aws sso login`, keys, instance role). A 401 or 403 under SigV4 points at
  the AWS identity and docs/aws-permissions.md.

### Warehouse values

- Glue default catalog: the AWS account ID, such as `123456789012`.
- S3 Tables through Glue: `<account>:s3tablescatalog/<table-bucket>`, AWS's "nested catalog in a
  specific account" form.
- Use `service = "glue"` for both. `service = "s3tables"` is for the S3 Tables endpoint itself.

### Exceptions to AGENTS.md the AWS chain needs

- **File reads:** aws-config reads `~/.aws/config`, `~/.aws/credentials`, the SSO token cache,
  the web-identity token file, and the OS trust store for its own HTTPS client.
- **Plain HTTP:** the instance, ECS and EKS credential endpoints are link-local, plain-HTTP AWS
  services.
- **No shelling out:** profiles that use `credential_process` aren't supported, because Iceblink
  doesn't run external programs.

## Consequences

- **Tested by known answers.** Three signatures (long-term keys, a session token, and a table
  name with a space and a percent sign) match curl 8.7.1's independent SigV4 implementation.
  That method reproduces AWS's published `get-vanilla` vector exactly. A wiremock test checks the
  wire path `my%20table%25` and the canonical `my%2520table%2525`. A TRACE capture finds no
  secret key, session token or signature in any log line.
- **What to watch upstream.** If iceberg-rust ships SigV4 or encodes path segments itself,
  revisit: drop Iceblink's name encoding first, because double-encoding a name would break it.
- **Upstream.** The drafted comment for issue #1236 records what Iceblink needed: the hook, path
  encoding, and HTTP status in `iceberg::Error`.
